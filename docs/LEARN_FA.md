# درس عملی ساخت بک‌اند Python برای TalentFlow

هدف این پروژه فقط یادگرفتن یک route نیست. می‌خواهیم ببینیم **وقتی یک درخواست دوبار رسید یا ذخیره‌سازی وسط کار شکست خورد، داده چگونه درست می‌ماند**. این موضوع در APIهای کاری، ثبت سفارش، پردازش فایل و برنامه‌های Agent هم مهم است.

## ۱ مسیر درخواست را بشناس

مرورگر به سرور رابط کاربری پیام می‌دهد. آن سرور کلید محرمانه را اضافه می‌کند و پیام را به FastAPI می‌فرستد. FastAPI درخواست را بررسی می‌کند و منطق کار داخل تراکنش SQLite اجرا می‌شود. پاسخ موفق بعد از commit برمی‌گردد.

فایل‌ها را به این ترتیب بخوان:

۱. `examples/offline_demo.py` برای دیدن مسیر کامل بدون HTTP.
۲. `talentflow/domain.py` برای قوانین استخدام و مصاحبه.
۳. `talentflow/store.py` برای ذخیره و تکرار درخواست.
۴. `talentflow/api.py` و `models.py` برای مرز HTTP و اعتبارسنجی.
۵. `tests/test_backend.py` برای دیدن مثال‌های موفق و ناموفق.

## ۲ FastAPI چه چیزی اضافه می‌کند

FastAPI در این پروژه درگاه HTTP است. تابع داخلی ساخت شغل با endpoint یکسان نیست؛ endpoint اول دسترسی، نوع محتوا و ورودی را بررسی می‌کند، بعد تابع کاری را اجرا می‌کند. Pydantic نام action و شکل شناسهٔ درخواست را بررسی می‌کند؛ قوانین هر عملیات در domain هستند. بنابراین «JSON معتبر» الزاماً «تصمیم استخدام مجاز» نیست.

در `/docs` شکل envelope را می‌بینی. برای فیلدهای هر action، `docs/API.md` را هم بخوان. API عمداً همان قرارداد action-based رابط قبلی را نگه می‌دارد؛ این تنها روش طراحی REST نیست.

## ۳ ماشین حالت یعنی چه

یک پرونده نمی‌تواند از هر وضعیت به هر وضعیت برود. ابتدا پیشنهاد می‌شود؛ مسئول انسانی آن را برای مصاحبه تأیید یا رد می‌کند. پس از تکمیل پاسخ‌ها، گزارش آماده می‌شود و دوباره تصمیم انسانی لازم است.

**تمرین:** در تست، تلاش کن پروندهٔ `suggested` را مستقیم `hired` کنی. انتظار خطای ۴۰۹ داریم و وضعیت قبلی باید باقی بماند. این محدودیت یک قانون کاری است، نه صرفاً بررسی نوع داده.

امتیاز این پروژه ماک است: تطبیق واژه‌ای مهارت‌ها و طول پاسخ. نمرهٔ زیاد به معنی شایستگی فرد نیست؛ برای آموزش مسیر استفاده شده است.

## ۴ تراکنش چه مشکلی را حل می‌کند

فرض کن ساخت شغل دو ثبت لازم دارد: خود شغل و رسید درخواست. اگر اولی ثبت شود ولی دومی شکست بخورد، تلاش مجدد ممکن است کار را دوباره انجام دهد. در این پروژه هر دو در یک تراکنش قرار دارند: یا هر دو ثبت می‌شوند یا هیچ‌کدام.

`BEGIN IMMEDIATE` پیش از خواندن وضعیت، تراکنش نوشتن را آغاز می‌کند. وقتی دو درخواست هم‌زمان به همان فایل SQLite می‌رسند، نویسنده‌ها نوبتی می‌شوند. این رفتار برای همین ذخیره‌سازی محلی است؛ تراکنش توزیع‌شده بین چند سرویس نیست.

**تمرین:** تست `test_receipt_and_record_rollback_together_on_storage_failure` را بخوان. یک trigger آزمایشی ثبت رسید را خراب می‌کند. بعد بررسی می‌کنیم که حتی شغل هم باقی نمانده باشد. این از تستِ «فقط کد ۲۰۰ برگشت» قوی‌تر است.

## ۵ Idempotency با retry فرق دارد

Retry یعنی دوباره تلاش کردن. Idempotency در قرارداد ما یعنی یک عملیات با شناسه و محتوای یکسان، دوباره رکورد نسازد.

برای ساخت شغل `requestId` بفرست. بار اول نتیجه ثبت می‌شود. بار دوم با همان شناسه و همان محتوا، پاسخ اصلی برمی‌گردد. اگر عنوان را تغییر دهی اما همان شناسه را نگه داری، خطای ۴۰۹ می‌گیری؛ چون معلوم نیست منظورت ادامهٔ قبلی است یا عملیات تازه.

**نکته:** اگر در هر تلاش یک شناسهٔ تازه تولید کنی، سرور نمی‌تواند بفهمد منظورت همان عملیات قبلی بوده است. شناسه را برای هر کار منطقی بساز و در retry همان را نگه دار.

پاسخ replay می‌تواند قدیمی باشد؛ برای دیدن وضعیت فعلی `snapshot` بگیر. این دو درخواست هدف یکسان ندارند.

## ۶ چرا توکن مصاحبه را سرور می‌سازد

اگر مرورگر بتواند توکن دلخواه انتخاب کند، حدس‌زدن یا تکرار توکن ممکن است دسترسی را خراب کند. اینجا Python با `secrets.token_hex(32)` توکن می‌سازد. هر درخواست داوطلب باید توکن را همراه داشته باشد و سرور انقضای هفت‌روزه را دوباره بررسی می‌کند.

کلید مدیر با توکن مصاحبه فرق دارد: اولی دسترسی گستردهٔ محلی دارد، دومی فقط برای همان مصاحبه است. هیچ‌کدام را در کد عمومی یا عکس خروجی نشان نده. دیتابیس این نمونه توکن‌ها را بدون رمزگذاری ذخیره می‌کند و باید مثل اطلاعات دسترسی از فایل آن محافظت کرد.

## ۷ اجرا و تمرین پیشنهادی

پس از نصب طبق README:

```bash
python examples/offline_demo.py
python -m pytest -q
```

دمو دادهٔ ساختگی را در دیتابیس موقت می‌سازد و در پایان پاک می‌کند. در حالت سرور، داده در مسیر `TALENTFLOW_DB` باقی می‌ماند.

سه تمرین کوچک:

- یک شغل با requestId ثابت بساز؛ دو بار تکرار کن و تعداد شغل‌ها را ببین.
- با همان requestId، عنوان شغل را عوض کن؛ خطای ۴۰۹ و باقی‌ماندن دادهٔ قبلی را بررسی کن.
- قبل از پاسخ همهٔ سؤال‌ها پایان مصاحبه را درخواست کن؛ انتظار رد شدن عملیات را داشته باش.

## سؤال مرور

۱. اگر پاسخ شبکه قطع شود، آیا حتماً داده ثبت نشده است؟
۲. چرا ذخیرهٔ رسید و شغل در دو تراکنش جدا می‌تواند مشکل بسازد؟
۳. چرا `confirmed: "true"` با `confirmed: true` یکی نیست؟
۴. چرا نمرهٔ مصاحبه نباید خودش تصمیم استخدام را ثبت کند؟
۵. فرق تست HTTP با تست تابع domain چیست؟

## مرحلهٔ بعدی یادگیری

بعد از فهم این نسخه، یک تمرین مناسب تبدیل ذخیرهٔ JSON به جدول‌های رابطه‌ای با migration است. سپس می‌توان user/role و محدودیت نرخ را طراحی کرد. اتصال مدل واقعی باید پس از مشخص‌شدن قرارداد خروجی، روش ارزیابی و مرز تصمیم انسانی انجام شود، نه صرفاً با جایگزینی نام provider.
